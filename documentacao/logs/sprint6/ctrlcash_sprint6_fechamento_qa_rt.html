Referências

1. Introdução

Este relatório documenta a Sprint 6 do CashCtrl, aplicativo móvel desenvolvido em Flutter com backend Firebase, dedicada ao fechamento do projeto: correção dos defeitos críticos remanescentes de navegação, perfil e salvamento de dados, auditoria completa das rotas de escrita do Firestore (toMap/fromMap × regras de segurança), adequação do código à execução na web e o ciclo final de QA automatizado em preparação às builds de distribuição.

Todo o conteúdo reflete o código efetivamente entregue na data de 27/10/2026: nomes de arquivos, classes, assinaturas, mensagens de erro e microcopy foram extraídos diretamente do repositório, e cada correção afirmada neste relatório foi reverificada no código antes de ser documentada. O relatório segue o padrão dos anteriores da biblioteca (Sprint 2 — Proposta A, Sprint 3 — RT v2 e Sprint 4 — Módulo Comparativo), continuando a numeração de tabelas e figuras a partir do fim do RT anterior, com Figuras 21–23 específicas das telas finais.

2. Resumo Executivo

A sprint de fechamento dividiu-se em três etapas internas (nomeadas Sprint 1, 2 e 3 desta fase), nas quais foram corrigidos quatro bugs de severidade alta ou crítica:

  • Botão voltar morto na tela de auditoria de preços (/audit-logs) — o usuário podia ficar preso na tela sem saída conhecida;
  • Duplicação de oferta em upsertOffer quando o fornecedor era renomeado (deduplicação incorreta pelo nome);
  • Perda de campos (generatedFrom, skippedOccurrences, receiptUrl, budgetId) ao editar uma transação recorrente;
  • Salvamento do perfil que não refletia campos apagados, com falha de carregamento sem recuperação oferecida ao usuário.

Ao final da fase, o aplicativo está livre de dart:io (executa na web), com upload de arquivos unificado via StorageService.uploadBytes (putData), suíte de testes em 128/128 (12 arquivos de teste), dart analyze com apenas 1 info pré-existente (deprecação da API updateEmail do Firebase Auth), e QA manual documentado tela a tela (seção 8). A identidade visual do app — paleta escura verde/dourada e logo camaleão — foi preservada integralmente, com o acréscimo controlado do camaleão dourado apenas no Dashboard.

3. Sprint 1 — Correções Críticas

3.1 Botão voltar morto na tela de auditoria

Sintoma: na tela de Auditoria (/audit-logs, audit_logs_screen.dart, AppBar criada com AppBrandedHeader(title: 'Auditoria', showBack: true)), o botão voltar podia não ter efeito: chegando à tela por navegação sem pilha (ex.: o acesso antigo do drawer via pushReplacementNamed), o pop não tinha para onde ir.

Causa raiz: composição de dois fatores.

  • O acesso antigo "Histórico de preços" do drawer navegava com pushReplacementNamed, que remove da pilha a tela anterior — não havia para onde voltar;
  • o cabeçalho AppBrandedHeader não tinha plano de saída quando a pilha de navegação está vazia (nada a fazer pop).

Correção: o leading de AppBrandedHeader em modo showBack (app_branded_header.dart, linhas 38–45) passou a testar a pilha:

if (Navigator.of(context).canPop()) {
  Navigator.of(context).pop();
} else {
  Navigator.of(context).pushNamedAndRemoveUntil(
    '/dashboard',
    (route) => false,
  );
}

Com o fallback, qualquer sub-tela aberta por pushReplacementNamed (sem histórico) ou diretamente (sem pilha) sempre oferece uma saída determinística para o Dashboard.

3.3 Camaleão dourado no Dashboard

O Dashboard (home_screen.dart, linha 66) passou a exibir a logo camaleão em dourado na AppBar (AppBrandedHeader(goldLogo: true)). Para tanto, AppBrandedHeader recebeu o parâmetro opcional goldLogo (padrão false, efeito nulo nas demais telas):

Figura 21. Camaleão dourado no Dashboard (ColorFiltered com AppColors.gold). [captura de tela pendente]

goldLogo
    ? ColorFiltered(
        colorFilter: const ColorFilter.mode(
          AppColors.gold,   // Color(0xFFB89775)
          BlendMode.srcIn,
        ),
        child: Image.asset('assets/images/logo.png', …),
      )
    : Image.asset('assets/images/logo.png', …)

BlendMode.srcIn aplica tint colorido preservando a silhueta: todo o traço do camaleão é pintado com o dourado institucional 0xFFB89775 (lib/theme/app_colors.dart, AppColors.gold) — o mesmo dourado já usado nos acentos do app, sem introduzir cor nova na paleta.

A decisão foi intencionalmente local: somente home_screen.dart passa goldLogo: true. Todas as demais AppBars mantêm a logo original (goldLogo: false) e o drawer preserva o logo_drawer.png original. Paleta e identidade camaleão ficaram inalteradas.

3.4 Perfil: salvamento fiel e estado de erro com "Tentar novamente"

O método _save da tela de edição de perfil (edit_profile_screen.dart) agora monta o objeto AppUser direto dos controllers, em vez de herdar campos parciais da sessão:

final updated = AppUser(
  uid: current.uid,
  nome: _nomeController.text.trim(),
  email: current.email,
  empresa: _empresaController.text.trim(),
  cnpj: _cnpjController.text.trim(),
  segmento: _segmentoController.text.trim(),
  telefone: _telefoneController.text.trim(),
  endereco: _enderecoController.text.trim(),
  photoUrl: _photoUrl,
  notifOrcamento: current.notifOrcamento,
  notifRecorrentes: current.notifRecorrentes,
  notifMargem: current.notifMargem,
);

Consequências:

  1. campos apagados persistem como string vazia ('') — nunca mais um valor antigo "vazando" pela fusão do documento (SetOptions(merge: true) em FirestoreService.saveUser) quando o usuário apagou o campo;
  2. flags de notificação preservadas (notifOrcamento, notifRecorrentes e notifMargem copiadas do perfil atual);
  3. toast antes do pop: AppToast.success(context, 'Perfil atualizado!') só então Navigator.pop(context) — o aviso de sucesso não depende de um contexto já desfocado;
  4. estado de erro funcional: quando prov.user == null (falha de carregamento do Firestore), a tela mostra o ErrorState (lib/widgets/error_state.dart) com message: prov.profileError ?? 'Perfil não carregado.' e botão "Tentar novamente" chamando await prov.reloadProfile() (UserProvider, que reexecuta loadProfile(uid)).

3.5 StorageService: falha explícita com causa

Os métodos do StorageService (lib/services/storage_service.dart) passaram a re-throw com causa legível:

catch (e) {
  throw Exception('Falha no upload: $e');
}

deleteFile lança 'Falha ao excluir arquivo: $e'. Em vez de falhas silenciosas ou exceções de rede/Storage enterradas, as telas (cadastro, perfil, produto, scanner) mostram ao usuário cadeias de erro legíveis com a causa real no final (por exemplo, "Erro ao enviar foto: $e" no fluxo de cadastro).

4. Sprint 2 — Integridade de Salvamento

4.1 Bug de deduplicação por nome do fornecedor (applyOfferUpsert)

Bug de severidade ALTA. O upsertOffer (firestore_service.dart) deduplicava pelo nome do fornecedor normalizado (trim().toLowerCase()); ao editar uma oferta trocando o nome do fornecedor, a rotina não encontrava equivalente e criava uma segunda oferta em vez de atualizar, duplicando o item no array.

Correção (lógica pura): o upsert foi extraído para uma função pura e testável applyOfferUpsert(current, offer, {required newOfferId, now?}) em lib/utils/offer_rules.dart, retornando OfferUpsertResult(offers, offerId, isCreate, previous):

  1. match por id prioritário (indexWhere((o) => o.id == offer.id)) — edição idempotente: renomear o fornecedor atualiza a oferta no lugar, preservando createdAt e a posição;
  2. fallback de upsert por fornecedor normalizado (mantido para novos cadastros de mesma parceria);
  3. teto de 15 ofertas preservado (ensureOfferLimit com StateError('Limite de 15 ofertas por insumo atingido.'));
  4. ordem do array preservada (substituição in-place, sem reordenação);
  5. a primeira oferta do insumo nasce ativa (isFirst → isActive: true), com activeOfferId correspondente no serviço;
  6. o batch de auditoria fica intacto: upsertOffer (firestore_service.dart, a partir da linha 267) consome o OfferUpsertResult e grava o documento do insumo e o log offer.create/offer.update no mesmo WriteBatch, sem mudança de comportamento nas price_audit_logs.

Testes: 8 testes novos em test/offer_upsert_test.dart — entre eles "applyOfferUpsert nao duplica ao editar oferta trocando nome do fornecedor", "preserva ordem das ofertas ao atualizar pelo meio", "lanca StateError ao tentar criar alem do limite de 15" e "atualizar fornecedor sem mudar preco mantem previousPrice igual".

4.2 Preferências de notificação com rollback

A gravação das preferências (notifications_screen.dart, rota /settings/notifications) gravava os Switches otimistamente, sem esperar o resultado do Firestore — uma falha de rede deixava o exibido incoerente com o salvo.

Correção em dois pontos:

  • Provider (user_provider.dart, updateNotificationPrefs): guarda o snapshot previous, aplica o estado otimista, faz await _firestore.saveUser(updated); em falha restaura _user = previous (rollback) e rethrow — o estado exibido nunca fica inconsistente com o persistido;
  • Tela: await provider.updateNotificationPrefs(orcamento/recorrentes/ margem: …) por switch, indicador "Salvando..." durante a gravação (linha 152) e, no catch, AppToast.error(context, 'Erro ao salvar preferência: $e') com a causa legível.

4.3 Cadastro: erro final com detalhe da causa

O catch final do fluxo de cadastro (cadastro_screen.dart) mostra agora a causa real, além das mensagens amigáveis dos tipos específicos:

catch (e) {
  _mostrarErro('Não foi possível concluir o cadastro: $e');
}

Os blocos on AuthException e on FirebaseAuthException mantêm as mensagens amigáveis existentes; o catch genérico vira último recurso legível (ex.: falha no upload da foto de perfil, indisponibilidade de rede), cobrindo inclusive o AppToast.error(context, 'Erro ao enviar foto: $e') do envio da foto.

4.4 Polish: toasts antes do pop nos formulários

Padronizado o padrão toast-antes-do-pop: AppToast.* é emitido antes de Navigator.pop(context), garantindo que o feedback fique visível na tela de destino, não perdido no stack em desfoco. Os cinco formulários principais adotam o padrão:

  1. transaction_form_screen.dart — "Transação registrada!" / "Transação atualizada!";
  2. budget_form_screen.dart;
  3. ingredient_form_screen.dart;
  4. offer_form_screen.dart;
  5. product_form_screen.dart.

Complemento: edit_profile_screen.dart ("Perfil atualizado!") segue o mesmo padrão e cadastro_screen.dart emite AppToast.success(context, 'Cadastro realizado com sucesso!') antes de pushNamedAndRemoveUntil('/dashboard', …) — o Dashboard abre já com o aviso de confirmação.

5. Sprint 3 — Auditoria de Persistência e Compatibilidade Web

5.1 Auditoria completa de escrita (models × regras)

Foi realizada auditoria completa cruzando rotas de escrita do Firestore × modelos (toMap/fromMap) × regras de segurança:

  • firestore.rules — as 6 coleções (users, transactions, budgets, ingredients, products, price_audit_logs) permanecem isoladas por UID com users/{uid}/...; transactions mantém a validação de domínio nas regras (amount is number && amount > 0 — RN01); a subcoleção price_audit_logs é append-only (leitura e criação para o dono; update/delete: if false);
  • storage.rules — isolamento por UID em users/{uid}/{allPaths=**} e bloqueio genérico allow read, write: if false;
  • toMap/fromMap — SEM mismatch: nenhum modelo escrito tem campo persistido fora do respectivo fromMap; o roundtrip foi coberto por test/model_roundtrip_test.dart.

5.2 Bug ALTO: edição de transação recorrente perdia campos

Bug de severidade ALTA. O _save da tela de transações (transaction_form_screen.dart) montava o AppTransaction sem copiar os campos de recorrência e anexos da transação em edição. Salvar a edição perdia:

  • generatedFrom (vínculo da instância gerada com a recorrente original);
  • skippedOccurrences (ocorrências puladas);
  • receiptUrl (foto do comprovante);
  • budgetId (vínculo com o orçamento).

Correção (linhas 112–125): os quatro campos são repassados de widget.editing:

final t = AppTransaction.create(
  id: widget.editing?.id ?? '',
  type: _type,
  category: _category,
  description: _descriptionController.text.trim(),
  amount: value,
  date: _date,
  paymentMethod: _paymentMethod,
  recurring: _recurring,
  recurrence: _recurrence,
  generatedFrom: widget.editing?.generatedFrom,
  skippedOccurrences: widget.editing?.skippedOccurrences ?? const [],
  receiptUrl: widget.editing?.receiptUrl,
  budgetId: widget.editing?.budgetId,
  notes: …,
);

Com isso, editar não apaga o vínculo da recorrência, o comprovante nem o vínculo com o orçamento.

5.3 Compatibilidade web (kIsWeb)

Adequação para build web, com diretriz central kIsWeb:

  • dart:io erradicado de lib/ — uma varredura por grep dart:io lib/ retorna vazio;
  • StorageService.uploadBytes (ref.putData(bytes, metadata)) criado como caminho único de upload — funciona em Android/iOS e web, sem depender de arquivos do sistema;
  • os pickers (image_picker) usam ImageSource.gallery quando kIsWeb (kIsWeb ? ImageSource.gallery : ImageSource.camera), sempre lendo XFile.readAsBytes() antes do uploadBytes (um único pipeline de bytes);
  • product_scanner_screen.dart ganhou guarda kIsWeb com corpo web dedicado (_buildWebBody, linha 391): digitar/colar o código do produto manualmente e ação "Escolher foto" pela galeria; as ações câmera e lanterna ficam explicitamente indisponíveis na web;
  • o upload do scanner segue o mesmo caminho unificado do StorageService adotado nas demais telas.

Resultado: o aplicativo não tem mais bloqueio tecnológico de dart:io para compilar em web, e as diferenças de plataforma ficam explícitas na interface.

5.4 Riscos registrados

Risco futuro baixo e registrado: updateTransaction, updateBudget e updateProduct persistem com doc.set(t.toMap()) sem merge. Hoje é coerente, pois os formulários gravam o payload completo do modelo. Mas, caso um modelo ganhe um campo novo no futuro, o set() sem merge sobrescreveria o documento e descartaria qualquer campo extra preexistente. Recomendação para a v-next: trocar para SetOptions(merge: true) (ou update()) nesses setters, com teste de integração que valide o payload completo.

9.2 .env e Firebase

Como registrado nos RTs anteriores (e em context/erros-a-evitar.md, §1.3), as credenciais do Firebase vivem apenas no .env e são lidas com flutter_dotenv em lib/firebase_options.dart; a segurança real vem das Regras (firestore.rules, storage.rules) — a API key é restrita ao projeto, não substitui as regras. No build web, as variáveis do .env são embutidas no bundle JS; essa decisão está documentada e aceita (§1.3 do "Erros a Evitar").

O .env é criado a partir de .env.example (valores vazios), com as mesmas chaves — não expostas neste documento.

9.3 Rodando e testando

Passo a passo (base de desenvolvimento):

$ flutter pub get      # restaura as dependências
$ dart analyze .       # verificação estática (workspace com "(Cópia)")
$ flutter test         # 128 testes / 12 arquivos

Android (dispositivo físico) — duas formas:

$ flutter run                          # dev direto no dispositivo conectado (USB/ADB)
$ flutter build apk --release          # gera build/app/outputs/flutter-apk/app-release.apk
$ adb install -r build/app/outputs/flutter-apk/app-release.apk   # instala o APK

O APK de release (seção 7.2) é assinado com chaves de debug — instalável para teste em dispositivo, não publicável na Play Store. A opção --split-per-abi gera variantes por arquitetura (v7a, v8a, x86_64), reduzindo o tamanho por APK.

Web (local) — duas formas:

$ flutter run -d chrome    # dev com hot reload no Chrome
$ flutter build web        # gera build/web/ (servir o diretório hospedando-o)

Para conferir o build pronto, servir o conteúdo de build/web/ por um servidor estático local e abrir no navegador (testar seções 5.3 e 8 nos pontos marcados como web).

Testes automatizados:

$ flutter test             # suíte completa: 128/128 (seção 6)

9.4 Deploy das regras (operação)

10. Apêndice iOS (não construído nesta fase)

O build iOS não foi realizado nesta fase por decisão do usuário: a máquina de desenvolvimento é Linux, sem Xcode, e a pasta ios/ não existe no repositório (apenas android/ e web/ presentes). Nenhum problema de código bloqueia o iOS — é dependência de ambiente. Checklist futuro resumido:

  1. flutter create --platforms=ios . para gerar o Runner iOS;
  2. criar o app iOS no console do Firebase (bundle identifier do projeto, atualmente com.example.ctrlcash em android/app/build.gradle.kts) e baixar o GoogleService-Info.plist para ios/Runner/;
  3. chaves no .env já válidas — o flutter_dotenv lê as mesmas credenciais (atenção ao reCAPTCHA/condições de login e-mail/senha no iOS);
  4. pod install no Mac (Xcode compatível) para os pods nativos (firebase_core, firebase_storage, notificações, mobile_scanner);
  5. flutter build ios --release (ou flutter build ipa --release) no Mac, gerando o artefato assinado.
